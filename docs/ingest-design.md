# JSON取り込み機能の設計記録（Phase 19）

この文書は、duckOrch に JSON 取り込み機能を実装したときの設計判断を、判断ごとに理由と根拠を添えて記録したものである。

根拠には手元の技術書を引いた。ただし本を読んでから設計したのではなく、設計して実装したあとに突き合わせた。したがって以下には、本と一致した判断だけでなく、本の助言に反した判断も、本が指摘する問題をまだ抱えたままの箇所も含まれる。参照した本の一覧と、どれを何に使ったかは末尾に置いた。

---

## 1. 作ったもの

DuckDB 拡張のプラグマ5本と、それを支える Rust クレート1本。

| プラグマ | 役割 |
|---|---|
| `orch_ingest_preview(path, target)` | どんな表ができるかだけを見る。書き込まない |
| `orch_ingest_run(path, target, ...)` | ファイル取り込み。追記・置換・併合 |
| `orch_ingest_http(url, target, ...)` | ページング付きAPI取得と取り込み |
| `orch_ingest_state` | 再開カーソルの一覧 |
| `orch_ingest_reset(source, resource)` | カーソルの破棄 |

やることは一言で言うと、入れ子のJSONを親子の表に開き、あとから増えた列を吸収し続ける、である。

```sql
PRAGMA orch_ingest_run('orders/*.jsonl', 'raw.orders');
PRAGMA orch_ingest_run('orders.jsonl', 'raw.orders',
                       disposition = 'merge', primary_key = 'id');
```

内部テーブルは5つ。

- `__orch__.ingest_schemas` — 形が変わったときだけ版を積む
- `__orch__.ingest_schema_changes` — 何が変わり、どのDDLで吸収したか
- `__orch__.ingest_loads` — 取り込み1回ごとの記録。失敗も残る
- `__orch__.ingest_state` — 再開カーソル
- `__orch__.ingest_fetches` — HTTP要求1回ごとの記録

## 2. 判断と根拠

### 2.1 入れ子を親子の表に開く

構造体は親の列に平坦化し、配列は子の表に逃がす。

```
{"id":1,"customer":{"name":"田中"},"items":[{"sku":"A-1"}]}

raw.orders          id, customer__name
raw.orders__items   _orch_parent_id, _orch_index, sku
```

これは第1正規形そのものである。

- 根拠: SQL Antipatterns 第1章「Jaywalking」（p.25-30）。1つの列に複数の値を詰める設計を否定し、交差テーブルへの分離を解として示す
- 根拠: Data Engineering Design Patterns 第8章「Normalizer」（p.260-265）。第1正規形を「繰り返し項目を持たず、各行が主キーで一意に識別できる状態」と定義し、繰り返し項目は専用の表に抽出せよとする

同書は同じ章で代償も明示している。正規化は結合コストを生む（p.264「Query cost」）。実際、この実装でも3階層のデータを1枚に戻すには結合が2回必要になる。

- 対案の存在: 同章「Denormalizer」（p.266-267）は、入れ子を構造体型のまま1列に保持する道も示す。DuckDB は構造体型を持つので、この道もあり得た

取らなかった理由は、利用者が普通のSQLを書けることを優先したためである。構造体のまま置くと、結合は消えるが、列アクセスの構文が独特になり、既存の可視化や集計がそのまま使えない。

なお、深さには上限を設けた（既定3）。超えた枝は展開せず、文字列として1列に畳む。これは Denormalizer 側への部分的な譲歩でもある。

### 2.2 行の識別子は取り込みIDと行番号から作る

`_orch_id` は `<取り込みID>#<行番号>`、子孫は `<親>/<位置>` を継ぎ足す。

当初は「行の内容のハッシュ」を考えたが、これは破棄した。列が1つ増えた瞬間に全行のハッシュが変わり、同一性の判定が総崩れになるためである。

- 根拠: Data Engineering Design Patterns 第4章「Keyed Idempotency」（p.100-104）。冪等な鍵を作るときは**不変な属性**を使えとし、イベント時刻のような可変値を使うと遅延データの到着で鍵が変わる事故（図4-8）を示す。同書は代わりに追記時刻・取り込み時刻を勧める

この実装の行番号と取り込みIDは、書き込んだ時点で確定し、二度と変わらない。同書のいう不変な属性にあたる。

同書はさらに「鍵の生成はファイルやパーティションにも同じ考え方で使える」（p.102）と述べており、この実装が取り込みIDでファイル群と行の両方を辿れるようにしているのは、その延長にある。

### 2.3 型推論を自前で書かない

JSONの中身は一切パースしない。DuckDB に読ませ、返ってきた型文字列だけを Rust に渡す。

```
read_json → DESCRIBE → 型文字列 → 型の木 → 表とSQL
```

理由は二重実装の回避である。JSONの型推論はすでに DuckDB が持っており、そこに独自実装を並べれば、必ず食い違う。

この判断のおかげで、新クレートは 2,169 行に収まった。判断を「型の木から表への写像」という純関数の問題に縮められたことが大きい。

- 関連: A Philosophy of Software Design 第4章「Deep modules」。良いモジュールとは、単純な入口の奥に多くの機能を隠したものであり、Unix のファイル入出力が5つの呼び出しで済んでいる例を挙げる。取り込みの入口を `orch_ingest_run(path, target)` の2引数に絞れたのは、型推論を外に出したことの結果でもある

### 2.4 スキーマ台帳を持ち、増えた列は吸収する

表の形が変わったときだけ版を積み、変更内容とDDLを別表に残す。列の追加と型の拡大は自動で吸収し、非互換な型変更は取り込みごと失敗させる。

- 根拠: Delta Lake: The Definitive Guide 第5章「Schema Enforcement and Evolution」（p.93-95）。書き込み時にスキーマを検査する方式を説明し、自動吸収の手軽さを認めつつ「驚きの変更を後から巻き戻すほうが、結局は高くつく」と警告する。だから同書は、自動吸収に頼りきらず、どの列が来る想定かを把握せよと勧める

この実装が「吸収はするが、必ず記録する」形にしたのは、この警告への回答である。吸収と可視化を両立させれば、あとから巻き戻す必要が減る。

- 根拠: Data Engineering Design Patterns 第9章「Schema Compatibility Enforcer」（p.284-289）。強制の方式を3つに分類する。外部サービス方式、挿入時の暗黙方式、DDL契約方式。この実装は暗黙方式に、明示的な版管理を足したものにあたる
- 根拠: Fundamentals of Data Engineering 第5章（p.170）。文書データベースの例として、まさに `name` が構造体で `favorite_bands` が配列という形を挙げ、スキーマ進化が下流の取り込みを壊すと述べる

契約の強さを2値（受け入れる／止める）にした点は、意図的に本より単純にしている。同書は互換性のモードを後方・前方・完全と3つ挙げるが、この実装の利用者は取り込む側であって、消費者との契約を結ぶ立場ではない。区別しても使い分けが生まれない。

一方、本が指摘していてこの実装が満たしていない点もある。

- Schema Migrator（同書 p.290-292）は、列の改名を「新列を足し、猶予期間を置き、旧列を消す」手順として定義する。この実装に改名の概念はなく、改名は「消失＋追加」に見える。旧列は残ってNULLを取るので壊れはしないが、対応関係は記録されない

### 2.5 書き込み方式は「先に入れて、あとで刈る」

追記・置換・併合の3方式を、いずれも「まず全部追記し、方式に応じて不要な行を消す」形に統一した。

理由は、比較の時点で新しい行がすでに表にあるため、取得元を二度読む必要も、一時領域に溜める必要もないからである。

- 関連: Data Engineering Design Patterns 第2章「Full Loader」（p.9）。全置換で drop-and-insert を使うと、読み手が空の状態を見る危険があると警告し、トランザクションか、公開用のビューを介した切り替えを勧める

この実装は前者を採る。すべてを1つのトランザクションに入れているので、読み手が中間状態を見ることはない。

- 根拠: Data Engineering Design Patterns 第4章「Transactional Writer」（p.105-109）。全か無かの意味論を、書き手側の冪等性の道具として位置づける。ただし同書は「冪等性はトランザクションの範囲に限られる」とも釘を刺す

この釘は当たっている。この実装で追記を2回実行すれば、行は2倍になる。冪等なのは1回の取り込みが途中で落ちた場合だけで、同じファイルを二度流す操作は冪等ではない。冪等にしたければ併合を使い、主キーを指定する必要がある。

- 対案: 同章「Proxy」（p.110-111）は、書き込みのたびに版付きの表を作り、ビューで最新だけを見せる方式を示す。履歴を全部残せる利点があるが、表が無限に増える。取らなかった

### 2.6 併合は一時表を使わない

削除対象の行集合を一時表に溜めず、副問い合わせとして各削除文に直接埋め込んだ。

理由は DuckDB の制約である。一時表は `temp` カタログに属し、1つのトランザクションが2つのカタログに書くことを DuckDB は許さない。宛先が接続済みカタログ（例えば DuckLake）のとき、一時表を使うと必ず失敗する。

これは机上では見つからず、カタログ宛のテストを書いて初めて出た。台帳の書き込みをコミット後にずらしたのも同じ理由である。

### 2.7 識別子は正規化して必ず引用符で囲む

列名は取得元のJSONのキーから来る。つまり外部データが識別子になる。

- 根拠: SQL Antipatterns 第21章「SQL Injection」（p.246-247）。プレースホルダと文字列エスケープは**値**を守るが、表名・列名・キーワードは守れないと明言する。同書の解は、利用者の入力を直接埋めず、あらかじめ定義した候補に写像すること

この実装では候補表を持てない。列名は事前に分からないからである。代わりに二段構えにした。

1. 正規化 — 英数字と下線以外を下線に置換する。引用符やセミコロンはこの時点で消える
2. 引用 — 生成時に必ず二重引用符で囲み、内部の引用符は二重化する

さらに、大文字小文字だけが違うキーは DuckDB では衝突するため、正規化後に検出して接尾辞を付ける。

### 2.8 資格情報は値でなく名前で持つ

HTTP取得のトークンは、DuckDB のシークレット管理から名前で引く。タスクの記述にもテーブルにもトークンは残らない。

- 根拠: Data Engineering Design Patterns 第7章「Secrets Pointer」（p.226-227）。資格情報はどこにも保存せず、参照だけを持てとする。同書は同じ節で「安心してログに書いてしまう」危険も指摘する
- 根拠: OAuth 2 in Action。アクセストークンを問い合わせパラメータに載せると、アクセスログに残り、そのまま公開の場に貼られる事故に繋がると述べる

この実装がトークンを要求ヘッダにのみ載せ、URLに載せないのは、この2点への対応である。ただし取得記録（`ingest_fetches`）にはURLをそのまま保存しているので、利用者が `token=` を含むURLを手で渡した場合は残ってしまう。これは残った穴である。

- 上位の方式: 同書「Secretless Connector」（p.228-231）は、そもそも資格情報を持たず、実行主体の身元で認可する方式を勧める。クラウド前提の話であり、単一ファイルで完結する道具には持ち込めなかった

### 2.9 取り込んだ表を資産として登録する

取り込みが終わると、各表が資産として登録され、材質化履歴・親子の辺・取得元への上流辺が入る。

- 根拠: Data Engineering Design Patterns 第10章「Dataset Tracker」（p.321-324）。データセット間の依存グラフを持つことを、観測可能性の一部として位置づける
- 根拠: Fundamentals of Data Engineering 第2章（p.38）。スキーマ進化・データフロー・系譜のメタデータを取得しているかを、設計時の問いとして挙げる

この実装で取得元を `file://` や `http://` の形で上流に置いたのは、外部の入口をグラフの端点として明示するためである。

### 2.10 上限は必ず報告する

HTTP取得のページ数には上限がある（既定100）。上限に達して打ち切った場合、`truncated` として記録し、要約にも出す。

黙って切り捨てると、不完全な取り込みが完全に見える。これは本の指摘というより、実装方針として最初に決めた。

## 3. 本の助言に反した判断

### 3.1 HTTP取得層を自前で作った

- 反した根拠: Fundamentals of Data Engineering 第7章「APIs」（p.254）。「車輪を再発明するな」と述べ、管理サービスが高く見えても、自分の時間の価値と、API接続を書くことの機会費用を考えよと勧める。同書は、既存の枠組みが対応していないAPIにだけ自前の接続を残せとする

私も同じ判断で、当初は取得層を作らないよう提案した。実装量が最も重く、差別化にならず、単一ファイルで完結するという道具の立ち位置からも外れるためである。

依頼者はそれを承知のうえで全部作るよう指示した。したがって作った。ただし範囲は意図的に絞ってある。

- ページングは4方式のみ
- 認証はベアラトークンのみ
- 上限に達したら止めて報告する
- 再試行は5xxと通信断のみ。4xxは即座に失敗させる

同書のいう「まだ十分にある、枠組みが対応していないAPI」に対する最小限の道具、という位置づけである。

### 3.2 エラーの行を退避する仕組みを作らなかった

- 満たしていない根拠: Data Engineering Design Patterns 第3章「Dead-Letter」（p.40-45）。処理できないレコードを捨てず、専用の場所に退避して、あとから調べられるようにするパターン

この実装に該当する仕組みはない。型が非互換なら取り込み全体が失敗し、ロールバックする。1行だけ壊れているデータに対しては、全部を止めるという強い挙動になる。

取得したファイルは削除せず残しているので、原因の特定は可能である。ただし「壊れた行だけを外して残りを通す」ことはできない。

## 5. 残っている課題

本と突き合わせて明確になった穴を、優先度順に並べる。

1. 壊れた行の退避がない。1行の不正が取り込み全体を止める（Dead-Letter 相当が未実装）
2. 列の改名を改名として扱えない。消失と追加に見える（Schema Migrator 相当が未実装）
3. 同じファイルを二度流す操作が冪等でない。追記のみの場合、行が重複する
4. 取得記録にURLをそのまま保存している。利用者がURLに資格情報を含めた場合、残る
5. 実サービスに対するHTTP取得の検証がない。確認はローカルAPIまで

1と2は本に明確な処方がある。3は併合を使えば回避できるが、既定の追記でその挙動になることを利用者が知る必要がある。
